#### RISK-001: 前置依赖检查（原"校验逻辑迁移遗漏"）

**优化方案**：
- ❌ **移除**：独立的校验逻辑和 Validator Agent
- ✅ **简化为**：直接检查上一阶段的输出文档是否存在
- ✅ **执行方式**：读取文档即可，无需复杂校验

**工作流程描述**：
```
Skill 执行前检查：
  1. 检查上一阶段输出文档是否存在
  2. 读取文档内容
  3. 确认文档格式完整（有内容即可）
  4. 开始执行当前 Skill
```

**示例**：
- Skill2 执行前：检查 Skill1 的输出文档 `boundary.md` 是否存在
- 如存在 → 直接读取并执行 Skill2
- 如不存在 → 提示"前置依赖缺失，请先执行 Skill1"

#### RISK-002: 工作流过程描述（原"交互逻辑内嵌冲突"）

**优化方案**：
- ❌ **移除**：代码层面的交互逻辑内嵌
- ✅ **简化为**：工作流过程中的交互节点描述
- ✅ **执行方式**：在 Skill 定义中描述交互时机和方式

**工作流程描述**：
```
Skill 执行过程中的交互：
  1. 检测信息缺失/模糊
  2. 触发定向提问（工作流描述）
  3. 等待用户回复
  4. 解析用户输入
  5. 更新产物内容
```

**示例**（在 Skill 定义中描述）：
```markdown
### 步骤 4：用户交互
- 检测关键字段是否缺失
- 如缺失，发起定向提问：
  - 问题模板：「请补充{字段名}的具体描述」
  - 等待用户输入
  - 解析并补充到产物中
```

#### RISK-003: 人工审查流程（原"评审机制性能问题"）

**优化方案**：
- ❌ **移除**：性能优化考虑
- ✅ **简化为**：人工审查文档流程
- ✅ **执行方式**：用户评审文档内容，确认或提出修改意见

**工作流程描述**：
```
Skill 输出后的评审：
  1. 展示产物文档给用户
  2. 用户审查文档内容
  3. 用户决策：
     - 确认 → 继续下一个 Skill
     - 修改 → 提出修改意见，优化后重新评审
     - 新增想法 → 补充到文档中，重新评审
  4. 记录评审结果
```

**评审提示模板**（工作流描述）：
```
【需求分析-{阶段}-{Skill}】- 用户评审

{Skill 名称}已完成，输出产物如下：

{产物文档内容}

---
请评审以上结果：
- 输入「确认」表示无误，继续执行下一个步骤
- 输入「修改」并提供修改意见，格式：「修改：{具体修改内容}」
- 输入「新增」并提出新想法，格式：「新增：{新需求内容}」
```

**优化方案**：
- ❌ **移除**：复杂的状态文件 Schema 设计
- ✅ **简化为**：工作任务的 Todo-List 列表
- ✅ **执行方式**：管理工作任务进度，而非技术状态

**Todo-List 结构设计**：
```markdown
# 工作任务清单 - {PlanID}

## 基本信息
- Plan 名称：{产品名称}
- 开始日期：{日期}
- 当前状态：执行中/已完成/已暂停
- 执行模式：常规模式/轻量化模式

## 任务列表

### S0 阶段：Plan 制定
- [ ] Skill0: Plan 制定
  - 状态：待执行/执行中/已完成
  - 输出文档：plan.md
  - 评审状态：待评审/已通过/需修改
  - 完成时间：{日期时间}

### S1 阶段：需求边界与原始采集
- [ ] Skill1: 需求边界界定
  - 状态：待执行/执行中/已完成
  - 输入文档：plan.md
  - 输出文档：boundary.md
  - 评审状态：待评审/已通过/需修改
  - 完成时间：{日期时间}

...（更多 Skill）
```

**Todo-List 管理规则**：
1. **任务状态**：
   - 待执行 → 前置任务未完成
   - 执行中 → 当前正在执行
   - 已完成 → 产物已生成，等待评审
   - 已评审 → 用户已确认通过

2. **评审状态**：
   - 待评审 → 等待用户审查
   - 已通过 → 用户确认无误
   - 需修改 → 用户提出修改意见
   - 修改中 → 正在根据意见优化

3. **进度追踪**：
   - 总任务数：13 个 Skill
   - 已完成：X 个
   - 已评审：Y 个
   - 进度：X/13 (XX%)
