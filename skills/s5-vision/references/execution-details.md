# S5-A01 执行详细步骤

## 步骤 1：前置校验

**目标**：验证前置产物是否完整、格式是否正确

**操作**：
1. 检查需求分析阶段产物是否存在
2. 检查产物状态是否为 completed
3. 检查产物 ID 是否匹配且连续
4. 验证 Markdown 报告格式是否规范

**验证规则**：
- 所有前置产物必须存在（S1-S4阶段产物）
- 产物状态必须为 completed
- 需求规格说明书（SRS）内容完整

**错误处理**：
- 产物缺失 → 返回错误 E001，要求先完成需求分析阶段
- 格式错误 → 返回错误 E002，要求重新生成前置产物
- 状态异常 → 返回错误 E003，要求检查产物状态

---

## 步骤 2：读取需求产物

**目标**：加载所有需求分析阶段产物内容

**操作**：
1. 读取需求规格说明书（SRS）
2. 读取用户故事清单
3. 读取非功能需求
4. 读取约束条件
5. 读取风险评估报告
6. 读取技术可行性报告
7. 建立需求追溯索引

**验证规则**：
- 文件必须可读
- 内容必须完整
- 编码必须为 UTF-8

**错误处理**：
- 文件读取失败 → 返回错误 E101，重试 3 次
- 内容解析失败 → 返回错误 E102，尝试修复或中止

---

## 步骤 2.5：用户交互（信息补全与澄清）

**目标**：在架构愿景定义过程中，当遇到信息不完整或需要用户确认的场景时，主动与用户交互

**触发场景**：

| 场景 | 说明 | 示例 |
|------|------|------|
| 系统特征不明确 | 需求中系统类型、规模等特征模糊 | "高并发"未定义具体指标 |
| 架构方向有多个选项 | 系统特征支持多种架构风格 | 可选分层架构或微服务 |
| 约束条件缺失 | 关键约束未明确 | 部署方式、技术栈约束 |
| 非功能需求模糊 | 性能、可用性等指标不明确 | "高可用"未定义SLA |

**交互流程**：遵循 [execution-flow-standard.md](../../_shared/execution-flow-standard.md) 中的"用户交互标准流程"章节

**使用模板**：
- 使用 [user-interaction/clarification-template.md](user-interaction/clarification-template.md) 进行信息澄清
- 使用 [user-interaction/information-collection-template.md](user-interaction/information-collection-template.md) 收集补充信息
- 使用 [user-interaction/option-selection-template.md](user-interaction/option-selection-template.md) 进行选项选择

## 步骤 3：自动识别系统特征

**目标**：基于需求内容自动分析系统特征

**操作**：
1. 分析系统类型（Web应用/移动应用/桌面应用/嵌入式/大数据）
2. 评估用户规模（内部使用/部门级/企业级/互联网级）
3. 分析数据特征（数据量、数据类型、数据关系复杂度）
4. 评估性能要求（响应时间、并发量、吞吐量）
5. 分析集成需求（外部系统数量、集成复杂度）
6. 判定安全等级（公开/内部/敏感/机密）

**分析维度说明**：

| 分析维度 | 分析内容 | 输出 |
|----------|----------|------|
| **系统类型** | Web应用/移动应用/桌面应用/嵌入式/大数据 | 系统类型判定 |
| **用户规模** | 内部使用/部门级/企业级/互联网级 | 规模等级判定 |
| **数据特征** | 数据量、数据类型、数据关系复杂度 | 数据特征判定 |
| **性能要求** | 响应时间、并发量、吞吐量要求 | 性能等级判定 |
| **集成需求** | 外部系统数量、集成复杂度 | 集成等级判定 |
| **安全等级** | 公开/内部/敏感/机密 | 安全等级判定 |

**验证规则**：
- 每个维度必须有明确的判定结果
- 判定结果需要有依据

---

## 步骤 4：自动推导架构方向

**目标**：基于系统特征自动推导架构建议

**操作**：
1. 根据系统类型推荐架构风格
2. 根据性能等级推荐技术策略
3. 根据数据特征推荐存储方案
4. 记录推导理由和依据

**架构风格推荐规则**：

| 系统类型 | 推荐架构风格 | 理由 |
|----------|--------------|------|
| 企业Web应用 | 分层架构 | 结构清晰，易于维护 |
| 高并发互联网应用 | 微服务架构 | 水平扩展，独立部署 |
| 实时数据处理 | 事件驱动架构 | 异步处理，高吞吐 |
| 复杂业务系统 | 领域驱动设计 | 业务对齐，易于演进 |
| 移动端应用 | 前后端分离 + BFF | 适配多端，统一接口 |

**性能等级推荐规则**：

| 性能等级 | 推荐策略 |
|----------|----------|
| 低（<100并发） | 单体应用，简单缓存 |
| 中（100-1000并发） | 应用集群，数据库优化 |
| 高（1000-10000并发） | 分布式缓存，读写分离 |
| 极高（>10000并发） | 微服务，分库分表，消息队列 |

**数据特征推荐规则**：

| 数据特征 | 推荐存储方案 |
|----------|--------------|
| 关系型数据为主 | 关系数据库（PostgreSQL/MySQL） |
| 文档型数据为主 | 文档数据库（MongoDB） |
| 海量日志数据 | 时序数据库（InfluxDB/TimescaleDB） |
| 复杂关系查询 | 图数据库（Neo4j） |
| 混合数据类型 | 多存储组合（Polyglot Persistence） |

**验证规则**：
- 推荐结果必须有明确的理由说明
- 推荐理由需与系统特征匹配

---

## 步骤 5：识别决策点

**目标**：识别需求中不明确或需要权衡的决策点

**操作**：
1. 分析系统特征是否存在多个可行方案
2. 识别技术栈选择的决策点
3. 识别部署方式的决策点
4. 识别数据一致性策略的决策点
5. 识别安全等级的决策点

**常见决策点清单**：

| 决策类型 | 触发条件 | 需要用户确认 |
|----------|----------|--------------|
| 架构风格选择 | 系统同时具有多种特征时 | 最终选择 |
| 技术栈选择 | 存在多个同等可行的技术选项 | 基于团队能力选择 |
| 部署方式 | 云原生 vs 传统部署 | 基于基础设施选择 |
| 数据一致性策略 | 强一致性 vs 最终一致性 | 基于业务容忍度选择 |
| 安全等级 | 安全需求描述模糊时 | 明确安全要求 |

**决策优先级**：

| 优先级 | 决策项 | 影响 |
|:------:|--------|------|
| P0 | 架构风格 | 全局影响，难以变更 |
| P1 | 技术栈 | 影响开发效率和团队学习成本 |
| P2 | 部署方式 | 影响运维复杂度 |
| P3 | 详细设计 | 可在实现阶段调整 |

---

## 步骤 6：用户交互确认

**目标**：针对识别出的决策点，与用户交互确认

**操作**：
1. 整理决策点清单
2. 为每个决策点准备选项和说明
3. 向用户展示并请求选择
4. 记录用户决策

**交互方式**：

**方式1：提供选项**
- 列出可行方案（通常2-3个）
- 说明每个方案的优缺点
- 提供适用场景说明
- 请求用户选择

**方式2：询问澄清**
- 描述模糊的需求
- 列出可能的解释选项
- 请求用户明确

**方式3：确认假设**
- 列出基于分析做出的假设
- 请求用户确认或纠正

**交互流程**：遵循 [execution-flow-standard.md](../../_shared/execution-flow-standard.md) 中的"用户交互标准流程"章节

---

## 步骤 7：生成架构愿景

**目标**：基于自动分析和用户确认，生成架构愿景

**操作**：
1. 整合系统特征分析结果
2. 整合架构方向推导结果
3. 整合用户决策确认结果
4. 生成架构愿景文档

**架构愿景内容结构**：

1. **系统定位**
   - 系统类型和范围
   - 目标用户群体
   - 核心价值主张

2. **架构目标**
   - 功能性目标
   - 非功能性目标（性能、可用性、安全性等）
   - 目标优先级

3. **架构原则**
   - 基于系统特征选择适用的原则
   - 原则优先级

4. **关键决策**
   - 已确认的架构决策
   - 决策理由

5. **风险与假设**
   - 识别的架构风险
   - 设计假设

**验证规则**：
- 架构愿景内容完整
- 决策理由清晰
- 风险识别充分

---

## 步骤 8：后置校验

**目标**：验证产物完整性和正确性

**校验内容**：
- 架构愿景文档已生成且格式正确
- 所有必填章节已填写
- 系统特征分析完整
- 架构决策记录完整
- Todo-List 可更新

**错误处理**：
- 产物文件不存在 → 返回错误 E201，重新生成
- Markdown 格式错误 → 返回错误 E202，修复格式
- 必填字段缺失 → 返回错误 E203，补充后重新生成
- Todo-List 结构错误 → 返回错误 E204，检查结构

---

**目标**：更新Todo-List，标记 S5-A01 完成，准备用户评审
