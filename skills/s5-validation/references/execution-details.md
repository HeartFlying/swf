# S5-A06 详细执行步骤说明

本文档包含 S5-A06 架构验证与评审的详细执行步骤（对应 SKILL.md Section 3.2）。

---

## 步骤 1：前置校验

**校验内容**：

- 所有 S5 阶段架构产物文件存在性检查
- 架构产物文件格式校验（Markdown 格式）
- Todo-List 文件存在性检查
- S5-A05 任务状态校验（应为"已完成"）

**错误处理**：

- 架构产物文件不存在：返回错误码 E001，提示"请先完成对应的架构设计 Skill"
- 文件格式错误：返回错误码 E003，提示"架构产物格式不符合要求"
- Todo-List 文件不存在：返回错误码 E003，提示"请先初始化 Todo-List"
- 前置任务未完成：返回错误码 E005，提示"请先完成 S5-A05 部署架构设计"

---

## 步骤 2：读取所有架构产物

**读取内容**：

- 架构愿景文档：提取系统定位、架构目标、设计原则、约束条件
- 架构视图设计文档：提取逻辑视图、进程视图、实现视图、部署视图、场景视图
- 数据架构设计文档：提取数据模型、存储方案、数据流转
- 接口架构设计文档：提取接口规范、API 设计、集成方案
- 部署架构设计文档：提取部署模式、服务架构、CI/CD 设计
- 需求规格说明书：提取功能需求、非功能需求
- 风险清单（如有）：提取已识别风险

**输出**：结构化的架构信息对象

---

## 步骤 2.5：用户交互（决策点确认）

**触发场景**：

- 检测到高风险架构决策需要确认
- 架构产物中存在相互冲突的决策
- 质量属性验证发现严重问题
- 检测到架构反模式需要确认处理方式

**交互流程**：

使用 [execution-flow-standard.md](../../_shared/execution-flow-standard.md) 中的标准用户交互流程：

1. 识别需要确认的决策点
2. 生成确认问题（使用标准化问题模板）
3. 等待用户输入
4. 解析用户输入，补充到验证对象
5. 如仍不清晰，进行多轮对话（最多 3 轮）

**交互模板**：

- **需求澄清**：使用 [user-interaction/clarification-template.md](user-interaction/clarification-template.md)
- **信息收集**：使用 [user-interaction/information-collection-template.md](user-interaction/information-collection-template.md)
- **方案选择**：使用 [user-interaction/option-selection-template.md](user-interaction/option-selection-template.md)

**交互记录保存**：

所有交互记录保存到架构验证报告的"用户交互记录"章节。

## 步骤 3：架构完整性验证

### 3.1 设计产物完整性检查

| 检查项 | 检查内容 | 通过标准 |
|--------|----------|----------|
| 架构愿景 | 目标、原则、约束是否明确 | 所有关键决策已记录 |
| 逻辑视图 | 核心模块、职责划分 | 模块边界清晰，职责单一 |
| 进程视图 | 并发处理、通信机制 | 并发策略明确，无竞态风险 |
| 实现视图 | 代码组织、构建系统 | 分层清晰，依赖合理 |
| 部署视图 | 运行环境、资源配置 | 部署方案可行，资源充足 |
| 数据视图 | 数据模型、存储方案 | 数据一致性策略明确 |
| 接口规范 | API设计、集成方案 | 接口完整，规范统一 |

### 3.2 架构元素覆盖检查

| 架构元素 | 检查内容 | 状态 |
|----------|----------|------|
| 组件清单 | 所有组件已识别并定义 | 待检查 |
| 接口清单 | 组件间接口已定义 | 待检查 |
| 数据流 | 关键数据流已映射 | 待检查 |
| 控制流 | 关键控制流已映射 | 待检查 |
| 部署单元 | 部署单元与组件映射 | 待检查 |
| 配置项 | 所有配置项已识别 | 待检查 |

**输出**：完整性检查结果报告

## 步骤 4：质量属性验证

基于 ISO/IEC 25010 质量模型，验证架构对非功能需求的满足度。

### 4.1 性能效率验证

| 验证项 | 验证方法 | 检查点 |
|--------|----------|--------|
| 响应时间 | 架构推演 | 关键路径是否有性能瓶颈 |
| 吞吐量 | 容量估算 | 系统最大处理能力是否满足需求 |
| 资源利用 | 资源估算 | CPU/内存/存储是否充足 |
| 并发处理 | 架构审查 | 并发策略是否合理 |

### 4.2 兼容性验证

| 验证项 | 验证方法 | 检查点 |
|--------|----------|--------|
| 接口兼容 | 规范审查 | API版本策略是否明确 |
| 数据兼容 | 模型审查 | 数据迁移策略是否定义 |
| 平台兼容 | 技术栈审查 | 依赖组件版本兼容性 |

### 4.3 可用性验证

| 验证项 | 验证方法 | 检查点 |
|--------|----------|--------|
| 故障恢复 | 架构推演 | 单点故障是否有冗余 |
| 容错处理 | 异常场景分析 | 故障隔离和降级策略 |
| 可恢复性 | 备份策略审查 | 数据备份和恢复方案 |

### 4.4 安全性验证

| 验证项 | 验证方法 | 检查点 |
|--------|----------|--------|
| 认证授权 | 安全架构审查 | 身份验证和权限控制 |
| 数据保护 | 数据流审查 | 敏感数据加密和脱敏 |
| 通信安全 | 网络架构审查 | 传输层加密和证书管理 |
| 审计追踪 | 日志设计审查 | 操作日志和安全审计 |

### 4.5 可维护性验证

| 验证项 | 验证方法 | 检查点 |
|--------|----------|--------|
| 模块化 | 架构审查 | 模块耦合度和内聚性 |
| 可测试性 | 测试策略审查 | 测试覆盖率和自动化程度 |
| 可扩展性 | 扩展场景推演 | 水平/垂直扩展能力 |

### 4.6 可移植性验证

| 验证项 | 验证方法 | 检查点 |
|--------|----------|--------|
| 环境适配 | 部署架构审查 | 环境差异抽象程度 |
| 配置管理 | 配置策略审查 | 配置外部化程度 |

**输出**：质量属性验证结果矩阵

## 步骤 5：架构风险识别

### 5.1 技术风险识别

| 风险类别 | 风险描述 | 风险等级 | 缓解措施 |
|----------|----------|----------|----------|
| 性能风险 | 高并发场景下的性能瓶颈 | 高/中/低 | 缓存、异步、分片 |
| 可用性风险 | 单点故障、依赖故障 | 高/中/低 | 冗余、熔断、降级 |
| 安全风险 | 数据泄露、未授权访问 | 高/中/低 | 加密、认证、审计 |
| 技术债务 | 过时技术、复杂依赖 | 高/中/低 | 技术升级、重构 |
| 扩展风险 | 架构难以水平扩展 | 高/中/低 | 微服务化、无状态化 |

### 5.2 架构反模式检测

| 反模式 | 描述 | 检测方法 | 改进建议 |
|--------|------|----------|----------|
| 大泥球 | 模块间高度耦合 | 依赖分析 | 重构模块边界 |
| 金锤子 | 过度使用某种技术 | 技术栈审查 | 选择合适工具 |
| 烟囱系统 | 系统间无法集成 | 接口审查 | 标准化接口 |
| 资源池耗尽 | 连接池/线程池配置不当 | 配置审查 | 合理配置资源 |
| 级联故障 | 缺乏故障隔离 | 依赖分析 | 熔断降级机制 |
| 数据孤岛 | 数据无法共享 | 数据架构审查 | 统一数据模型 |

### 5.3 架构坏味道检测

| 坏味道 | 症状 | 影响 | 重构建议 |
|--------|------|------|----------|
| 循环依赖 | 模块A依赖B，B依赖A | 难以测试和部署 | 引入抽象层 |
| 上帝组件 | 单个组件职责过多 | 难以维护和扩展 | 拆分组件 |
| 知识泄露 | 下层知道上层细节 | 违反分层原则 | 依赖倒置 |
| 过早抽象 | 为不存在的需求抽象 | 增加复杂度 | 延迟抽象 |

**输出**：风险识别报告

## 步骤 6：架构决策验证

### 6.1 关键决策完整性检查

| 决策领域 | 决策项 | 状态 | 理由充分性 |
|----------|--------|------|------------|
| 架构风格 | 单体/微服务/事件驱动 | 待检查 | 待评估 |
| 技术选型 | 语言/框架/数据库 | 待检查 | 待评估 |
| 数据存储 | SQL/NoSQL/混合 | 待检查 | 待评估 |
| 通信方式 | 同步/异步/混合 | 待检查 | 待评估 |
| 部署模式 | 容器/虚拟机/无服务器 | 待检查 | 待评估 |
| 安全策略 | 认证/授权/加密 | 待检查 | 待评估 |

### 6.2 决策理由评估

评估每个架构决策的理由是否充分：

- 是否基于需求分析
- 是否考虑了约束条件
- 是否评估了替代方案
- 是否记录了权衡过程

**输出**：决策验证结果矩阵

## 步骤 11：后置校验

**校验内容**：

- 架构验证报告已生成且格式正确（Markdown 格式）
- S5 阶段综合报告已生成且格式正确
- Todo-List 已更新且状态正确
- 所有必填字段已填充

**错误处理**：

- 产物文件不存在：返回错误码 E201，重新生成产物
- Markdown 格式错误：返回错误码 E202，重新生成产物文件
- 必填字段缺失：返回错误码 E203，补充缺失字段后重新生成
- Todo-List 结构错误：返回错误码 E204，重新更新 Todo-List

---

## 步骤 12：用户评审

**评审触发**：后置校验通过后

**评审展示**：

向用户展示以下内容：
- 架构验证报告核心内容摘要
- 关键发现和风险识别
- 质量属性验证结果
- 架构决策记录摘要
- Todo-List 更新状态

**用户决策选项**：

- **确认**：验证结果无误，完成 S5 阶段
- **修改（小修改）**：直接修改验证报告或综合报告
- **修改（大修改）**：返回步骤 1 重新执行
- **新增想法**：补充验证内容，更新报告

**评审提示模板**：

```
【架构验证完成 - 用户评审】

架构验证已完成，核心结果如下：

**完整性验证**：
- 产物完整性：{百分比}
- 元素覆盖度：{百分比}
- 缺失项：{数量}个

**质量属性验证**：
- 性能效率：{评分}
- 安全性：{评分}
- 可用性：{评分}
- 可维护性：{评分}

**风险识别**：
- 高风险：{数量}个
- 中风险：{数量}个
- 低风险：{数量}个

**关键决策**：{数量}个 ADR 已记录

---
请评审以上验证结果：
- 输入「确认」表示无误，完成 S5 阶段
- 输入「修改」并提供修改意见，格式：「修改：{具体意见}」
- 输入「新增」并补充内容，格式：「新增：{新内容}」

示例：
- 确认
- 修改：需要补充XX场景的风险分析
- 新增：需要验证YY质量属性
```

**评审结果处理**：

| 用户决策 | 处理逻辑 | 状态变更 |
|----------|----------|----------|
| 确认 | 保存产物，更新 Todo-List，S5 阶段完成 | 任务状态：已评审，评审状态：已通过 |
| 修改 - 小修改 | 直接修改产物，重新展示评审 | 任务状态：执行中，评审状态：需修改 |
| 修改 - 大修改 | 返回步骤 1 重新执行 | 任务状态：执行中，评审状态：需重做 |
| 新增想法 | 更新验证报告，重新展示评审 | 任务状态：执行中，评审状态：需修改 |

**评审记录填写**：

每次评审后，在 Todo-List 的"评审记录"章节添加记录。
