## 步骤 3：自动分析接口需求特征

**分析维度**：

| 分析维度 | 分析内容 | 输出 |
|----------|----------|------|
| **客户端类型** | Web/移动端/桌面端/IoT/第三方系统 | 客户端类型判定 |
| **实时性要求** | 实时/准实时/异步 | 通信模式判定 |
| **数据查询复杂度** | 简单CRUD/复杂关联/聚合分析 | 查询模式判定 |
| **集成场景** | 内部系统/外部SaaS/开放平台 | 集成类型判定 |
| **性能要求** | 延迟敏感/吞吐优先/普通 | 性能等级判定 |
| **安全等级** | 公开/内部/敏感/机密 | 安全等级判定 |

**分析方法**：

1. 遍历需求规格说明书中的非功能需求，提取性能、安全要求
2. 分析架构视图中的客户端类型和部署模式
3. 分析数据架构中的实体关系，判断查询复杂度
4. 检查是否有外部系统集成需求

## 步骤 4：自动推导接口技术方案

**接口风格选择矩阵**：

| 系统特征 | 推荐接口风格 | 理由 |
|----------|--------------|------|
| Web应用 + 标准CRUD | RESTful API | 成熟规范，易于理解 |
| 复杂查询 + 灵活数据需求 | GraphQL | 客户端驱动查询，减少往返 |
| 微服务 + 高性能内部通信 | gRPC | 二进制序列化，低延迟 |
| 实时通信 + 推送场景 | WebSocket | 全双工通信，实时推送 |
| 事件驱动 + 异步处理 | 消息队列（AMQP/MQTT） | 解耦生产消费，削峰填谷 |
| 文件传输 + 大流量 | 对象存储 + 预签名URL | 高效传输，减轻服务压力 |

**多风格组合策略**：

| 场景 | 推荐组合 | 分工说明 |
|------|----------|----------|
| 标准Web应用 | RESTful + WebSocket | 主要API + 实时通知 |
| 复杂数据应用 | RESTful + GraphQL | 简单操作 + 复杂查询 |
| 微服务架构 | gRPC（内部）+ RESTful（外部） | 内部高性能 + 外部兼容 |
| 实时协作应用 | WebSocket + RESTful | 实时同步 + 配置管理 |
| 开放平台 | RESTful + Webhook | API调用 + 事件回调 |

## 步骤 5：自动识别接口分组

**接口分组原则**：

- 按业务领域划分（对应限界上下文）
- 按用户角色划分（管理员/普通用户/系统）
- 按功能模块划分（认证/核心功能/管理功能）

**典型接口分组示例**：

| 分组名称 | 基础路径 | 说明 | 典型接口 |
|----------|----------|------|----------|
| 认证授权 | `/api/v1/auth` | 登录、注册、Token管理 | 登录、登出、刷新Token |
| 用户管理 | `/api/v1/users` | 用户CRUD、个人资料 | 列表、详情、更新、删除 |
| 核心资源 | `/api/v1/{resources}` | 主业务资源操作 | CRUD、搜索、批量操作 |
| 文件服务 | `/api/v1/files` | 上传、下载、管理 | 上传、下载、删除、预览 |
| 系统管理 | `/api/v1/admin` | 配置、监控、日志 | 配置管理、系统状态 |
| 实时通信 | `/ws` | WebSocket连接 | 连接、订阅、消息推送 |

## 步骤 6：自动设计接口规范

### 6.1 RESTful API 设计规范

**URL设计规范**：

| 规则 | 说明 | 示例 |
|------|------|------|
| 小写字母 | 统一使用小写 | `/api/v1/users` |
| 复数名词 | 资源使用复数形式 | `/users` 而非 `/user` |
| 层级关系 | 用路径表示关联 | `/users/{id}/orders` |
| 避免动词 | 用HTTP方法表示操作 | `GET /users` 而非 `/getUsers` |
| 过滤排序 | 用查询参数 | `/users?status=active&sort=-created_at` |
| 版本控制 | URL中包含版本 | `/api/v1/...` |

**HTTP方法使用规范**：

| 方法 | 用途 | 幂等性 | 示例 |
|------|------|--------|------|
| GET | 获取资源 | 幂等 | `GET /users/{id}` |
| POST | 创建资源 | 非幂等 | `POST /users` |
| PUT | 全量更新 | 幂等 | `PUT /users/{id}` |
| PATCH | 部分更新 | 非幂等 | `PATCH /users/{id}` |
| DELETE | 删除资源 | 幂等 | `DELETE /users/{id}` |

**状态码使用规范**：

| 状态码 | 使用场景 | 说明 |
|--------|----------|------|
| 200 OK | 成功响应 | 标准成功 |
| 201 Created | 创建成功 | 返回新资源 |
| 204 No Content | 删除成功 | 无返回体 |
| 400 Bad Request | 请求参数错误 | 客户端错误 |
| 401 Unauthorized | 未认证 | 需要登录 |
| 403 Forbidden | 无权限 | 权限不足 |
| 404 Not Found | 资源不存在 | 路径或资源不存在 |
| 409 Conflict | 资源冲突 | 重复创建等 |
| 422 Unprocessable | 业务逻辑错误 | 验证失败 |
| 429 Too Many Requests | 限流 | 请求过于频繁 |
| 500 Internal Error | 服务器错误 | 服务端异常 |

### 6.2 通用响应格式

**标准成功响应**：

```json
{
  "code": 200,
  "message": "success",
  "data": { },
  "timestamp": "2026-03-28T10:00:00Z",
  "request_id": "req_xxx"
}
```

**分页响应格式**：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "items": [],
    "pagination": {
      "page": 1,
      "size": 20,
      "total": 100,
      "total_pages": 5,
      "has_next": true,
      "has_prev": false
    }
  }
}
```

**错误响应格式**：

```json
{
  "code": 400,
  "message": "请求参数错误",
  "errors": [
    {
      "field": "email",
      "message": "邮箱格式不正确",
      "code": "invalid_format"
    }
  ],
  "timestamp": "2026-03-28T10:00:00Z",
  "request_id": "req_xxx"
}
```

## 步骤 7：自动设计认证授权方案

**基于安全等级推荐认证方案**：

| 安全等级 | 推荐方案 | 说明 |
|----------|----------|------|
| 公开 | 无认证/API Key | 简单场景 |
| 内部 | JWT | 有状态认证 |
| 敏感 | JWT + RBAC | 认证+授权 |
| 机密 | OAuth2/OIDC | 第三方认证集成 |

**JWT认证规范**：

| 组件 | 说明 |
|------|------|
| Token类型 | Access Token + Refresh Token |
| 签名算法 | RS256（推荐）或 HS256 |
| Access Token有效期 | 15分钟 - 2小时 |
| Refresh Token有效期 | 7天 - 30天 |
| Token传输 | HTTP Header: `Authorization: Bearer {token}` |

**权限控制模型选择**：

| 模型 | 适用场景 | 说明 |
|------|----------|------|
| RBAC | 角色明确的系统 | 基于角色的访问控制 |
| ABAC | 复杂权限场景 | 基于属性的访问控制 |
| ACL | 资源级权限 | 访问控制列表 |

## 步骤 8：自动设计集成接口

**集成接口设计清单**：

| 集成类型 | 设计要点 | 技术选择 |
|----------|----------|----------|
| 第三方登录 | OAuth2/OIDC流程 | 标准协议 |
| 支付集成 | 异步通知 + 幂等处理 | Webhook + 重试 |
| 消息推送 | 可靠投递保证 | 消息队列 |
| 文件存储 | 预签名URL | 对象存储 |
| 数据同步 | 增量同步 + 冲突处理 | 定时任务 + API |
| 事件回调 | 签名验证 + 重试机制 | Webhook |

**Webhook设计规范**：

| 要素 | 说明 |
|------|------|
| 签名验证 | HMAC-SHA256签名 |
| 重试机制 | 指数退避，最多3-5次 |
| 幂等处理 | 使用Idempotency-Key |
| 事件类型 | Event-Type Header标识 |
| 版本控制 | API版本兼容 |

## 步骤 14：用户评审
