## 功能描述

### 核心职责

Skill6负责基于多维度评估对需求进行优先级排序，确保资源投入的最优配置，包括：
1. **业务价值评估**：评估需求对业务目标的贡献度
2. **用户价值评估**：评估需求对用户体验的提升程度
3. **技术成本评估**：评估需求实现的技术难度和资源消耗
4. **风险评估**：评估需求实现过程中的风险因素
5. **综合优先级计算**：基于多维度评分计算最终优先级

### 输入输出

**输入**：
- 前置Skill产物：S4-S05需求分类梳理结果
- 包含内容：需求分类体系、SMART检查结果、需求依赖关系

**输出**：
- 需求优先级排序报告 (`database/stages/s4/{PlanID}-S4-S06-001-priority.md`)
- 优先级排序JSON (`database/stages/s4/{PlanID}-S4-S06-001-priority.json`)
- 更新status.json中S4-S06状态

## 执行流程

```
读取S4-S05分类产物
    ↓
提取所有需求条目及分类信息
    ↓
评估业务价值（1-5分）
    ↓
评估用户价值（1-5分）
    ↓
评估技术成本（1-5分，反向计分）
    ↓
评估风险因素（1-5分，反向计分）
    ↓
计算综合得分和优先级
    ↓
考虑依赖关系调整优先级
    ↓
生成优先级排序报告
    ↓
输出优先级JSON
    ↓
更新状态文件
    ↓
返回执行结果
```

## 详细规范

### 1. 评估维度定义（参考IEEE 29148-2011）

#### 1.1 业务价值评估 (BV - Business Value)

**评估标准**：

| 分值 | 等级 | 说明 | 判定标准 |
|------|------|------|---------|
| 5 | 极高 | 对业务目标有关键贡献 | 直接影响核心KPI，是产品核心竞争力 |
| 4 | 高 | 对业务目标有显著贡献 | 支持主要业务流程，提升关键指标 |
| 3 | 中 | 对业务目标有一般贡献 | 支持辅助业务流程，改善用户体验 |
| 2 | 低 | 对业务目标贡献较小 | 边缘功能，对业务影响有限 |
| 1 | 极低 | 对业务目标几乎无贡献 | 可有可无的功能 |

**评估要素**：
- 与产品愿景的契合度
- 对核心业务流程的支持程度
- 对收入/用户增长的影响
- 竞争优势的建立

#### 1.2 用户价值评估 (UV - User Value)

**评估标准**：

| 分值 | 等级 | 说明 | 判定标准 |
|------|------|------|---------|
| 5 | 极高 | 解决用户核心痛点 | 用户强烈需要，没有替代方案 |
| 4 | 高 | 显著提升用户体验 | 用户明确需要，有较好满意度 |
| 3 | 中 | 改善用户体验 | 用户有需求，但不是最紧迫 |
| 2 | 低 | 轻微改善体验 | 锦上添花的功能 |
| 1 | 极低 | 几乎无用户价值 | 用户感知不明显 |

**评估要素**：
- 用户需求的紧迫程度
- 影响的用户群体规模
- 用户满意度提升程度
- 用户流失风险降低

#### 1.3 技术成本评估 (TC - Technical Cost)

**评估标准**（反向计分，成本越高分值越低）：

| 分值 | 等级 | 说明 | 判定标准 |
|------|------|------|---------|
| 5 | 极低 | 实现成本很低 | 简单功能，1-3天可完成 |
| 4 | 低 | 实现成本较低 | 标准功能，1周内可完成 |
| 3 | 中 | 实现成本中等 | 有一定复杂度，2-4周 |
| 2 | 高 | 实现成本较高 | 复杂功能，1-2个月 |
| 1 | 极高 | 实现成本极高 | 技术挑战大，2个月以上 |

**评估要素**：
- 技术可行性评估结果（Skill11）
- 开发工作量估算
- 技术债务风险
- 团队技能匹配度

#### 1.4 风险评估 (RI - Risk)

**评估标准**（反向计分，风险越高分值越低）：

| 分值 | 等级 | 说明 | 判定标准 |
|------|------|------|---------|
| 5 | 极低 | 几乎无风险 | 技术成熟，需求明确 |
| 4 | 低 | 风险较低 | 有轻微不确定性 |
| 3 | 中 | 风险中等 | 存在一定技术或需求风险 |
| 2 | 高 | 风险较高 | 技术挑战或需求变更可能 |
| 1 | 极高 | 风险极高 | 可能导致项目延期或失败 |

**评估要素**：
- 需求风险清单（Skill7）
- 需求变更可能性
- 技术不确定性
- 外部依赖风险

### 2. 综合优先级计算

#### 2.1 计算公式

```
综合得分 = (BV × 权重BV + UV × 权重UV + TC × 权重TC + RI × 权重RI) / 4

其中：
- 权重BV = 0.30 (业务价值权重)
- 权重UV = 0.30 (用户价值权重)
- 权重TC = 0.25 (技术成本权重)
- 权重RI = 0.15 (风险权重)
```

#### 2.2 优先级等级划分

| 综合得分 | 优先级 | 代码 | 说明 | 处理策略 |
|---------|--------|------|------|---------|
| 4.5 - 5.0 | P0 - 最高 | PRI-P0 | 必须实现，核心需求 | 优先投入资源，确保交付 |
| 3.5 - 4.4 | P1 - 高 | PRI-P1 | 应该实现，重要需求 | 计划内实现，资源允许时优先 |
| 2.5 - 3.4 | P2 - 中 | PRI-P2 | 可以实现，一般需求 | 资源充裕时实现 |
| 1.5 - 2.4 | P3 - 低 | PRI-P3 | 可选实现，边缘需求 | 视情况决定是否实现 |
| 1.0 - 1.4 | P4 - 最低 | PRI-P4 | 暂缓实现，未来考虑 | 暂不实现，后续评估 |

### 3. 依赖关系调整规则

#### 3.1 强依赖调整

如果被依赖需求的优先级为PX，则依赖需求的优先级最高为PX+1

```
示例：
- R001 (被依赖) 优先级: P1
- R002 (依赖R001) 原始优先级: P0
- 调整后R002优先级: P1 (不能超过被依赖项)
```

#### 3.2 互斥需求处理

互斥需求组中，只保留优先级最高的需求，其他标记为P4或删除

```
示例：
- R003 优先级: P1
- R004 优先级: P2 (与R003互斥)
- 结果: 保留R003，R004标记为P4
```

#### 3.3 包含关系处理

父需求优先级应不低于子需求优先级

```
示例：
- R005 (包含R006) 原始优先级: P2
- R006 (被包含) 原始优先级: P1
- 调整后R005优先级: P1 (不能低于子需求)
```

### 4. SMART原则符合度加分

对于完全符合SMART原则的需求，综合得分额外加0.2分（最高不超过5.0）

| SMART符合项数 | 加分 |
|--------------|------|
| 5项全部符合 | +0.2 |
| 4项符合 | +0.1 |
| ≤3项符合 | +0.0 |

## 错误处理

### 前置校验错误

| 错误类型 | 错误码 | 处理策略 |
|----------|--------|----------|
| S4-S05产物不存在 | E601 | 返回错误，要求先执行Skill5 |
| S4-S05产物格式错误 | E602 | 返回错误，要求重新生成分类产物 |

### 执行过程错误

| 错误类型 | 错误码 | 处理策略 |
|----------|--------|----------|
| 评分数据缺失 | E701 | 使用默认值3分继续评估 |
| 依赖关系冲突 | E702 | 标记冲突，使用默认调整规则 |
| 计算结果异常 | E703 | 重新计算，检查权重配置 |

### 后置校验错误

| 错误类型 | 错误码 | 处理策略 |
|----------|--------|----------|
| 优先级JSON为空 | E704 | 返回警告，确认是否确实无需求 |
| 必填字段缺失 | E705 | 补充缺失字段 |
| 优先级分布异常 | E706 | 检查评分逻辑，确保合理性 |

**前置校验**：
- 检查S4-S05产物是否存在且格式正确

- 检查优先级JSON格式是否符合模板

- 当关键需求被降级时，请求用户确认
- 当互斥需求选择存在争议时，请求用户决策
