## 步骤 3：自动分析部署需求

**分析维度**：

| 分析维度 | 分析内容 | 输出 |
|----------|----------|------|
| **系统规模** | 用户量、并发量、数据量 | 规模等级判定（小型/中型/大型） |
| **可用性要求** | 可接受的停机时间 | SLA等级判定（99%/99.9%/99.99%） |
| **扩展性要求** | 是否需要自动扩缩容 | 弹性需求判定 |
| **预算约束** | 基础设施预算范围 | 成本等级判定（低/中/高） |
| **运维能力** | 团队运维经验水平 | 复杂度承受度判定 |
| **合规要求** | 数据本地化、安全认证 | 合规约束判定 |
| **技术偏好** | 云服务商偏好、技术栈 | 技术约束判定 |

## 步骤 4：自动推导部署模式

**部署模式选择矩阵**：

| 系统特征 | 推荐部署模式 | 理由 |
|----------|--------------|------|
| 小型应用 + 单机部署 | Docker Compose | 运维简单，资源占用低 |
| 中型应用 + 高可用要求 | Kubernetes (托管) | 自动恢复，水平扩展 |
| 大型应用 + 多云部署 | Kubernetes (多云) | 避免厂商锁定 |
| 无服务器 + 事件驱动 | FaaS (Lambda/Cloud Functions) | 按需付费，自动扩缩 |
| 传统应用 + 渐进迁移 | 虚拟机 + 容器混合 | 渐进式现代化 |
| 边缘计算 + 低延迟 | 边缘节点部署 | 靠近用户，降低延迟 |

**云服务选型矩阵**：

| 场景 | 推荐方案 | 适用云服务商 |
|------|----------|--------------|
| 全托管 + 快速上线 | PaaS (App Engine/Elastic Beanstalk) | AWS, Azure, GCP, 阿里云 |
| 容器化 + 简单编排 | 托管K8s (EKS/AKS/GKE) | AWS, Azure, GCP |
| 无服务器 | Lambda + API Gateway | AWS, 阿里云函数计算 |
| 国内部署 + 合规 | 阿里云/腾讯云/华为云 | 国内云服务商 |
| 混合云 | 私有云 + 公有云 | VMware + 公有云 |

## 步骤 5：自动设计服务架构

**容器化服务设计原则**：

- 单一职责：每个容器只运行一个进程
- 无状态化：应用层无状态，状态外置
- 不可变基础设施：镜像不可变，配置外部化
- 健康检查：每个服务提供健康检查端点

**典型服务清单模板**：

| 服务类型 | 服务名示例 | 说明 | 必需性 |
|----------|-----------|------|--------|
| 反向代理 | nginx/traefik | 流量入口、SSL终止、路由 | 必需 |
| 前端应用 | frontend/web | 静态资源、SPA应用 | 视架构 |
| 后端API | backend/api | 业务逻辑服务 | 必需 |
| 任务队列 | celery-worker/rq-worker | 异步任务处理 | 视需求 |
| 定时任务 | scheduler/cron | 定时任务调度 | 视需求 |
| 主数据库 | postgres/mysql | 主数据存储 | 必需 |
| 缓存 | redis/memcached | 会话、缓存、队列 | 推荐 |
| 搜索引擎 | elasticsearch | 全文检索 | 视需求 |
| 消息队列 | rabbitmq/kafka | 事件流处理 | 视需求 |
| 监控 | prometheus/grafana | 指标收集和展示 | 推荐 |
| 日志 | loki/fluentd | 日志收集和分析 | 推荐 |

## 步骤 6：自动设计网络架构

**网络分层设计**：

```
┌─────────────────────────────────────────────────────────────┐
│                        外部网络                              │
│                     (Internet/CDN)                          │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│                      边缘层                                  │
│            (WAF/DDoS防护/边缘缓存)                           │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│                      网关层                                  │
│         (负载均衡/API网关/SSL终止)                           │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│                      应用层                                  │
│              (容器/Pod/无服务器函数)                         │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│                      数据层                                  │
│            (数据库/缓存/对象存储/消息队列)                    │
└─────────────────────────────────────────────────────────────┘
```

**网络安全策略**：

| 层级 | 安全策略 | 说明 |
|------|----------|------|
| 边缘层 | DDoS防护、WAF规则 | 阻挡恶意流量 |
| 网关层 | 限流、认证、审计 | 访问控制 |
| 应用层 | 服务间mTLS、零信任 | 内部安全 |
| 数据层 | 加密存储、访问控制 | 数据保护 |

## 步骤 8：自动设计CI/CD流程

**CI/CD阶段设计**：

```mermaid
flowchart LR
    A[代码提交] --> B[构建阶段]
    B --> C[测试阶段]
    C --> D[安全扫描]
    D --> E[镜像构建]
    E --> F[推送镜像]
    F --> G[部署测试]
    G --> H[集成测试]
    H -->|通过| I[部署预发布]
    I --> J[验收测试]
    J -->|通过| K[部署生产]
    K --> L[健康检查]
    L -->|失败| M[自动回滚]
```

**CI/CD流水线阶段**：

| 阶段 | 任务 | 工具示例 |
|------|------|----------|
| Build | 代码编译、依赖安装 | Docker Build, Maven, npm |
| Test | 单元测试、覆盖率 | pytest, jest, junit |
| Security | 依赖扫描、SAST | Snyk, SonarQube, Trivy |
| Package | 镜像构建、推送 | Docker, Kaniko, BuildKit |
| Deploy Staging | 部署测试环境 | kubectl, helm, docker-compose |
| Integration Test | API测试、E2E测试 | Postman, Cypress, Selenium |
| Deploy Production | 部署生产环境 | 蓝绿部署/金丝雀发布 |
| Verify | 健康检查、冒烟测试 | 自动化探针 |

**部署策略选择**：

| 策略 | 适用场景 | 特点 |
|------|----------|------|
| 滚动更新 | 标准部署 | 逐步替换，零停机 |
| 蓝绿部署 | 需要快速回滚 | 双环境切换，即时回滚 |
| 金丝雀发布 | 风险控制 | 小流量验证，渐进放量 |
| 重建部署 | 开发环境 | 简单直接，有停机 |

## 步骤 9：自动设计监控告警方案

**可观测性三大支柱**：

| 支柱 | 监控内容 | 工具示例 |
|------|----------|----------|
| Metrics | 系统指标、业务指标 | Prometheus + Grafana |
| Logs | 应用日志、系统日志 | ELK/Loki + Grafana |
| Traces | 分布式追踪 | Jaeger/Zipkin/SkyWalking |

**关键监控指标**：

| 层级 | 指标类型 | 具体指标 |
|------|----------|----------|
| 基础设施 | 资源使用 | CPU、内存、磁盘、网络 |
| 应用 | 性能指标 | QPS、延迟、错误率 |
| 业务 | 业务指标 | 用户数、转化率、交易量 |
| 依赖 | 外部依赖 | 数据库连接、API调用 |

**告警分级策略**：

| 级别 | 触发条件 | 响应时间 | 通知方式 |
|------|----------|----------|----------|
| P0 | 服务完全不可用 | 5分钟 | 电话+短信+邮件 |
| P1 | 核心功能受损 | 15分钟 | 短信+邮件 |
| P2 | 性能下降 | 30分钟 | 邮件+IM |
| P3 | 预警提示 | 2小时 | 邮件 |

## 步骤 10：自动设计环境管理

**环境划分策略**：

| 环境 | 用途 | 配置特点 |
|------|------|----------|
| 开发环境 | 日常开发 | 本地/远程，数据可重置 |
| 测试环境 | 功能测试 | 与生产类似，数据隔离 |
| 预发布环境 | 发布前验证 | 与生产一致，数据脱敏 |
| 生产环境 | 正式服务 | 高可用，严格管控 |

**配置管理原则**：

- 配置外部化：使用环境变量或配置中心
- 敏感信息加密：密钥、密码使用Secret管理
- 环境差异最小化：仅必要配置不同
