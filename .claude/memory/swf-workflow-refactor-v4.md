# SWF 工作流重构 v4.0 总结

## 重构日期
2026-03-29

## 重构背景
基于软件研发流程最佳实践，对原工作流进行深度优化，主要解决：
1. S2（市场校验）位置不当，应在需求定义之前
2. S3阶段顺序不合理，风险识别应在技术选型之后
3. 缺少非功能需求专项分析
4. 缺少用户故事转换环节
5. 缺少测试策略设计

## 主要变更

### 1. 阶段顺序重构（S0-S2）

**原顺序**：S0→S1(需求)→S2(市场)→S3→S4
**新顺序**：S0→S1(市场)→S2(需求)→S3→S4

**Skill编号变更**：
| 原编号 | 新编号 | Skill名称 |
|--------|--------|-----------|
| S101 | S201 | 需求边界界定 |
| S102 | S202 | 显性需求提取 |
| S103 | S203 | 隐性需求挖掘 |
| S104 | S204 | 需求验证 |
| S201 | S101 | 竞品分析 |
| S202 | S102 | 市场痛点验证 |

### 2. S3技术规划阶段重构

**原顺序**：S301(风险)→S302(可行性)→S303(选型)
**新顺序**：S301(可行性)→S302(选型)→S303(NFR)→S304(风险)

**新增Skill**：S303 非功能需求定义
- 性能需求（响应时间、吞吐量、并发）
- 安全需求（认证、授权、加密、审计）
- 可用性需求（SLA、RTO、RPO）
- 可扩展性需求（容量规划、增长预期）
- 可维护性需求（代码质量、文档）

### 3. S4需求整合阶段增强

**新增Skill**：S405 用户故事编写
- 用户故事格式转换（As a... I want... So that...）
- 验收标准定义（Given-When-Then）
- 故事点估算
- 故事地图构建
- MVP范围确定

**编号调整**：S404(原型)→S406(原型)

### 4. S5-S6阶段增强

**S5-A06增强**：
- 增加技术债务识别与评估
- 增加ADR（架构决策记录）模板

**新增Skill**：S6-A04 测试策略设计
- 单元测试策略
- 集成测试策略
- 端到端测试策略
- 性能测试策略
- 安全测试策略
- 测试数据管理

## 新流程架构

```
S0: Plan制定 (S001)
  ↓
S1: 市场洞察 (S101竞品分析 → S102市场验证) [轻量化跳过]
  ↓
S2: 需求定义 (S201边界 → S202显式需求 → S203隐式需求[快速] → S204验证)
  ↓
S3: 技术规划 (S301可行性 → S302选型 → S303非功能需求 → S304风险)
  ↓
S4: 需求整合 (S401分类 → S402优先级 → S403核心需求 → S405用户故事 → S406原型[跳过])
  ↓
S5: 架构设计 (S5-A01愿景 → S5-A02视图 → S5-A03数据 → S5-A04接口 → S5-A05部署 → S5-A06验证)
  ↓
S6: 详细设计 (S6-A01模块 → S6-A02数据库 → S6-A03UI/UX → S6-A04测试策略)
  ↓
CM: 变更管理 (CM-001影响分析)
```

## 评审节点统计

- **常规模式**：26个Skill评审 + 6个阶段评审 + 1个最终评审 = **33个评审点**
- **轻量化模式**：20个Skill评审 + 6个阶段评审 + 1个最终评审 = **27个评审点**

## 轻量化模式跳过

- S101（竞品分析）
- S102（市场验证）
- S203（隐性需求挖掘）- 快速模式
- S406（原型设计）

## 关键优化价值

1. **市场驱动**：市场洞察前置，指导需求定义
2. **技术约束明确**：非功能需求在架构设计前明确
3. **敏捷支持**：用户故事直接支持迭代开发
4. **质量保障**：测试策略在详细设计阶段定义
5. **技术债务可控**：架构验证阶段识别技术债务
